## Overview

Exposes the World Bank Open Data API (Indicators API v2) for development economics research, policy analysis, and cross-country comparison workflows. Covers 29,500+ development indicators — GDP, poverty rates, health, education, energy, trade, infrastructure — for 200+ countries and aggregates over 60+ years of data. No authentication required.

Designed as the global complement to BLS (US detail) and EIA (US energy) — provides the international context those servers lack.

## Requirements

- Read-only throughout; no auth or write operations
- Indicator search must handle 29,500+ indicators: keyword search + topic/source filtering is the primary discovery path
- Country queries must support: individual ISO2/ISO3 codes, semicolon-separated multi-country lists, regional aggregates, income-level groups, and `all`
- Year range queries via `date=YYYY:YYYY`; most-recent-values shorthand via `mrv=N`
- Pagination via `page`/`per_page` on all list endpoints; max `per_page` = 1000 for data, no fixed cap on metadata; every page stays within the 50 KB output budget (see the output-budget decision), so a large `per_page` is served as a smaller, disclosed page rather than rejected
- No API key required; no rate-limit enforcement needed at server level
- Response data can be sparse: individual country×year cells may be `null` when the WDI doesn't have a value
- Aggregates (regions, income groups, World) are returned alongside individual countries in `all` queries; the server must communicate what type each entry is
- Poverty at a caller-chosen threshold, and the inequality distribution behind it, come from the Poverty and Inequality Platform rather than the WDI series — a second upstream API, with its own envelope, error convention, and survey coverage, and its aggregates on a separate endpoint
- The Bank's own lending operations are a third upstream API, on a different host again, keyed on ISO2 rather than ISO3 and answering an unmatched exact filter with a plain zero-hit rather than an error; the server must not let a bad filter value read as "no results"

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `WorldBankApiService` | World Bank Indicators API v2 (`https://api.worldbank.org/v2/`), including its source-scoped data API (`/v2/sources/{id}/...`) | All tools and resources; `worldbank_get_poverty` and `worldbank_search_projects` only for its country index (`lookupCountry`) |
| `PipService` | World Bank Poverty and Inequality Platform (`https://api.worldbank.org/pip/v1/`) | `worldbank_get_poverty` |
| `ProjectsService` | World Bank Projects API (`https://search.worldbank.org/api/v3/`) | `worldbank_search_projects` |

One service per upstream API. Every Indicators v2 endpoint shares a base URL and the `[paging, items]` envelope, so a single service covers that whole surface. PIP shares none of it — flat JSON array, no pagination, real HTTP status codes. Projects shares none of it either, and none of PIP's: a different host, results keyed by project ID in an object rather than listed, offset paging on `os`/`rows`, and a zero-hit where the others would error. Each gets its own client rather than an extension of `WorldBankApiService`, whose `buildUrl`, `fetchAllPages`, and `isWbErrorEnvelope` are all specific to Indicators v2. What the three share is the framework layer beneath them: `fetchWithTimeout`, `withRetry`, the init/accessor pattern, and HTML-error-page detection — every one of the three hosts serves an HTML error page on some failure.

## Implementation Order

1. Config (`src/config/server-config.ts`) — base URL, default page size
2. `WorldBankApiService` — typed fetch methods for each endpoint category, retry/timeout wiring
3. `worldbank_list_topics` + `worldbank_list_sources` — static reference data, simple to verify
4. `worldbank_list_countries` + `worldbank_get_country` — country metadata
5. `worldbank_search_indicators` + `worldbank_get_indicator` — indicator discovery
6. `worldbank_get_data` — primary data tool; most complex due to multi-country and aggregate handling
7. Resources — `worldbank://indicator/{id}` and `worldbank://country/{code}`
8. `PipService` + `worldbank_get_poverty` — a second upstream API with its own envelope, error convention, and survey-vs-gap-filled merge
9. `ProjectsService` + `worldbank_search_projects` — a third upstream API on its own host, with an ID-keyed result object, offset paging, and a zero-hit where the others error

Each step is independently testable against the live API.

## Domain Mapping

The API has four endpoint families. All return the same envelope: `[{ page, pages, per_page, total }, [...items]]`.

| Noun | Endpoint | Operations |
|:-----|:---------|:-----------|
| Indicator | `GET /v2/indicator` | list (paginated), filter by source (`?source=`). `?searchterm=` exists but does not filter — see the note under `worldbank_search_indicators`. |
| Indicator | `GET /v2/indicator/{id}` | get by ID |
| Indicator | `GET /v2/topic/{id}/indicator` | list indicators for a topic |
| Country | `GET /v2/country` | list (paginated); includes aggregates intermixed |
| Country | `GET /v2/country/{code}` | get by ISO2, ISO3, or aggregate code |
| Data | `GET /v2/country/{codes}/indicator/{id}` | query data; `{codes}` = single code, `;`-delimited list, or `all` |
| Data (source-scoped) | `GET /v2/sources/{id}/country/{codes}/series/{id}[/time/{tokens}][/{concept}/{value}]` | query one source's own dataset — the fallback for indicators the data endpoint answers with message id `175`; see the Source-scoped data API reference |
| Source layout | `GET /v2/sources/{id}/concepts`, `/v2/sources/{id}/{concept}` | a source's concepts, and the values of each (`country`, `time`, and its extra dimension) |
| Topic | `GET /v2/topic` | list all 21 topics |
| Source | `GET /v2/source` | list all ~71 sources |

Key query parameters for the data endpoint:

| Parameter | Format | Purpose |
|:----------|:-------|:--------|
| `date` | `YYYY`, `YYYYQ1`–`Q4`, `YYYYM01`–`M12`, or a range of two periods of the same type | Filter to a period or range. A window the API can't apply — no overlap with the series, or a granularity the series doesn't carry — is silently discarded upstream and the full series comes back, so the returned periods are checked against the requested ones locally |
| `mrv` | integer | Most recent N values (alternative to `date`) |
| `page` | integer | Pagination page |
| `per_page` | integer | Results per page (max: API allows up to 1000) |
| `format` | `json` | Always required |

The API returns country aggregates (regions, income groups, World) mixed with individual countries in `all` queries. Aggregate entries have `region.id = "NA"` and `incomeLevel.id = "NA"` in the country listing, making them identifiable.

## Workflow Analysis

### Common agent workflows

**Discover then query (most frequent path):**

| # | Call | Tool |
|:--|:-----|:-----|
| 1 | Search for indicator by concept | `worldbank_search_indicators` |
| 2 | Inspect metadata for the best match | `worldbank_get_indicator` (optional) |
| 3 | Query data for countries × years | `worldbank_get_data` |

**Topic-led discovery:**

| # | Call | Tool |
|:--|:-----|:-----|
| 1 | Browse topic list | `worldbank_list_topics` |
| 2 | Search indicators filtered to a topic | `worldbank_search_indicators` + `topic_id` |
| 3 | Query data | `worldbank_get_data` |

**Country profile:**

| # | Call | Tool |
|:--|:-----|:-----|
| 1 | List/find countries filtered by region or income level | `worldbank_list_countries` |
| 2 | Get full metadata for a specific country | `worldbank_get_country` (optional) |
| 3 | Query multiple indicators for that country | `worldbank_get_data` (repeated per indicator) |

**Cross-regional comparison:**

| # | Call | Tool |
|:--|:-----|:-----|
| 1 | Query indicator with regional aggregate codes | `worldbank_get_data` (countries = `EAS;LCN;MEA;SAS;SSF;ECS`) |
| 2 | Follow up with income-group breakdown | `worldbank_get_data` (countries = `LIC;LMC;UMC;HIC`) |

**Lending portfolio for a country:**

| # | Call | Tool |
|:--|:-----|:-----|
| 1 | Resolve the country's ISO3 or ISO2 code, if only a name is in hand | `worldbank_list_countries` or `worldbank_get_country` |
| 2 | Search the portfolio, narrowed by status and board-approval window | `worldbank_search_projects` |
| 3 | Re-run the narrowed search with `include_abstract` once the result set is small | `worldbank_search_projects` |

## Tool Specifications

### `worldbank_search_indicators`

Searches the 29,500+ indicator catalog. The critical discovery entry point — without this, an agent must already know an indicator's cryptic ID (e.g., `NY.GDP.PCAP.CD`).

**Input:**
- `query: string` — keyword terms, matched locally. Required unless `topic_id` or `source_id` is provided.
- `topic_id: string | undefined` — numeric topic ID (1–21) to filter by thematic area; the schema pattern admits digits only (blank reads as no filter). Use `worldbank_list_topics` to browse.
- `source_id: string | undefined` — numeric source ID to filter by dataset origin (e.g., `"2"` for World Development Indicators); digits only, like `topic_id`. Use `worldbank_list_sources` to browse.
- `page: number` (default: 1) — pagination page
- `per_page: number` (default: 50, max: 100) — results per page

**Note:** The API's `searchterm` parameter does not filter anything — a nonsense term returns the entire catalog, with or without a topic/source filter present. Keyword matching therefore happens entirely in the service, over the full candidate set for the requested scope: the whole catalog for a keyword-only search, `GET /v2/topic/{id}/indicator` for topic scope, `GET /v2/indicator?source={id}` for source scope, and `GET /v2/topic/{id}/indicator?source={id}` for both — the topic endpoint honors `source` the way `/indicator` does, intersecting the scopes and rejecting an unknown source ID. Each scope is fetched exhaustively (loop over the envelope's `pages`) before matching, so a hit on upstream page 2 is reachable. Matching is token-AND over an alphanumeric tokenization: the query is lowercased and split on every run of non-alphanumeric characters, and each resulting term must appear as a substring of the indicator's ID, name, or `sourceNote`. ID/name hits rank in six tiers — the query's normalized phrase equal to the ID or name; the name starting with the phrase as whole words, its last word allowed a plural `s` or `es` (`Life expectancy at birth` for `life expectancy`, ahead of `School life expectancy`; `Exports of goods and services` for `export`; not `Trademark applications` for `trade`); the phrase anywhere in `id name`; every term a whole word of `id name` (`co2` in `Carbon dioxide (CO2) emissions`, not inside `CO2e`); the remaining ID/name hits — then `sourceNote`-only hits. Within each tier, World Development Indicators (source 2) comes first, then other live sources, then archives (a source name matching `archive`, the test `preferredRow` applies), and catalog order breaks the remaining ties, except that a series family — IDs sharing their first three segments, within one tier and source rank — is gathered at its first member's place, fewest segments first. World Bank IDs mark a breakdown by sex, area, age, or quintile with an extra segment, so `EG.ELC.ACCS.ZS` leads `EG.ELC.ACCS.RU.ZS` and `.UR.ZS`, which the catalog lists ahead of it. Both sorts are stable, so only the order changes, never the set or `total`. Matching and ranking read the whole `sourceNote`. A query that tokenizes to nothing — punctuation only — is rejected before any fetch, since it has no term to match.

**Output:**
- `indicators: Array<{ id, name, sourceId, sourceName, topics[], sourceNote }>` — matching indicators; `sourceNote` is its first 150 characters, marked with `…` when longer (see the output-budget decision), on both surfaces. `worldbank_get_indicator` and the indicator resource return it whole.
- `total: number` — total matches before pagination
- `page: number`, `pages: number` — pagination state

**Errors:**
- `missing_filter` (`ValidationError`) — none of `query`, `topic_id`, `source_id` given. Recovery: supply one.
- `invalid_filter` (`NotFound`) — `topic_id` or `source_id` doesn't exist upstream (HTTP 200 with the error envelope, or HTTP 404 on the topic path), alone or combined. Recovery: browse valid IDs with `worldbank_list_topics` / `worldbank_list_sources`.
- `empty_query` (`ValidationError`) — `query` is non-blank but has no letters or digits (`!!!`, `()`). Recovery: provide a keyword, or omit `query` to browse by topic/source.

A search that matches nothing is not an error — it returns an empty `indicators` array with an `enrichment.notice` carrying the recovery hint.

### `worldbank_get_indicator`

Fetches complete metadata for a single known indicator ID.

**Input:**
- `indicator_id: string` — one indicator code (e.g., `NY.GDP.PCAP.CD`); the schema pattern admits letters, digits, `.`, `_`, and `-`. `all` fits that pattern and is refused in the handler as `multiple_indicators`

**Output:**
- `id, name, unit, sourceId, sourceName, sourceNote, sourceOrganization` — full metadata
- `topics: Array<{ id, name }>` — thematic categories

**Errors:**
- `indicator_not_found` (`NotFound`) — the API returns `{"message": [{"id": "120", "key": "Invalid value", "value": "The provided parameter value is not valid"}]}` for unknown indicator IDs (HTTP 200 with a message envelope). A path upstream can't route answers a real HTTP 404 instead; the service reads that as the same envelope. The service layer must detect both and throw `NotFound`. Recovery: use `worldbank_search_indicators` to find valid indicator IDs.
- `multiple_indicators` (`ValidationError`) — the ID is `all`, refused in the handler before any request, or upstream resolved it to rows carrying more than one distinct indicator ID. Recovery: pass one ID, or find indicators with `worldbank_search_indicators`.

`sourceNote` is plain text on this tool, `worldbank_search_indicators`, and the indicator resource: the shared normalizer turns `<br>`/`</br>` into a line break, drops other tags with their text kept, and decodes entities.

### `worldbank_get_data`

The primary data access tool. Queries indicator values for countries across a time range.

**Input:**
- `indicator_id: string` — one indicator code to query (e.g., `NY.GDP.PCAP.CD`), under the same pattern as `worldbank_get_indicator`. `.describe()` should include a format example and note to use `worldbank_search_indicators` to discover valid IDs.
- `countries: string | string[]` — one or more country codes. Pass a single code, an array, or one string separated by commas, semicolons, or pipes; the tool splits every string (array elements included) on all three through the shared `splitCountryCodes` (`src/services/worldbank/identifiers.ts`, which `worldbank_get_poverty` and `worldbank_search_projects` use too), drops blank segments, and sends the codes joined with `;` — the only separator the data endpoint accepts (a comma, literal or `%2C`, and a pipe are rejected as an invalid value). Lesotho goes into the path as `LSO` whatever the caller sent, because the API's edge firewall answers any country segment carrying `;LS` with HTTP 403; `appliedFilters.countries`, error messages, and rows keep the caller's codes and Lesotho's own. Accepts:
  - ISO2 codes (`US`, `CN`, `DE`)
  - ISO3 codes (`USA`, `CHN`, `DEU`)
  - Aggregate codes: region (`EAS`, `ECS`, `LCN`, `MEA`, `SAS`, `SSF`), income group (`HIC`, `UMC`, `LMC`, `LIC`), world (`WLD`)
  - `"all"` for all countries + aggregates (several hundred entries, varying by indicator; use pagination). It must stand alone: `all;US` is rejected upstream with the same envelope as a bad code, so the handler rejects `"all"` mixed with other codes (case-insensitively) as `mixed_all_selector` before the request rather than let it surface as `country_not_found` blaming valid codes.
  - At least one code is required. An empty array, an empty string, or any value that splits to no codes (`" ; "`, `","`, `"|"`, `[","]`) is a `ValidationError` — the API reads an empty path segment as every country, so silently widening would hand back an unrelated dataset. The array check runs on the split result, not the raw elements.
  - `.describe()` on this parameter should include examples of each form and note that `"all"` returns enough entries to require pagination. Don't pin a count — the row count varies by indicator.
- `date_range: string | undefined` — one period (`2020`, `2020Q1`, `2020M03`) or a range of two periods of the same type, earliest first (`2010:2023`, `2020Q1:2021Q4`, `2020M01:2020M06`). The shape is a schema `pattern`, so a malformed or mixed-type range is an `InvalidParams` rejection; a well-shaped range that runs latest first is rejected in the handler as `reversed_date_range`. Both happen before any request goes out. Mutually exclusive with `mrv`.
- `mrv: number | undefined` — the N most recent periods (1–100) holding a value for any requested country, clamped upstream to the length of the series; every requested country is returned at those periods, null where it has none (`ERI;SSD` with `mrv=2` gives both at 2015 and 2014, South Sudan's last years with data). Mutually exclusive with `date_range`.
- `dimension_value: string | undefined` — for an indicator answered by the source-scoped data API, the id of the value of its source's extra dimension (a WDI Database Archives release `202503`, a classification `PPPGlob` / `FPN 5.0`, a GDLD sector `WHT`, a counterpart area `265`), matched case-insensitively against the listing of every catalog source of the ID. Omitted or blank means the default for the concept (below). An id no listing carries is `unknown_dimension_value`; any value for an indicator the standard endpoint serves, or for a source with no extra dimension, is `dimension_not_applicable`.
- `page: number` (default: 1)
- `per_page: number` (default: 50, max: 1000) — a page holds at most 200 observations (`MAX_OBSERVATIONS_PER_PAGE`, see the output-budget decision). `WorldBankApiService.getData` reduces a larger size once, before any path runs, so the upstream `per_page`, the local slice of a re-read date window, and the source-scoped API's local slice all serve and count pages at 200; the served size is echoed as `appliedFilters.perPage` beside `requestedPerPage`, and `notice` discloses the reduction whenever the result runs past one page.

**Output:**
- `data: Array<{ countryCode, countryIso3, countryName, date, value, obsStatus, isAggregate, dimension? }>` — observations; `value` is `null` when WDI has no data for that cell. API source fields: `country.id` (ISO2) → `countryCode`, `countryiso3code` → `countryIso3`, `country.value` → `countryName`, each code completed from the cached country index the aggregate check already loads — upstream leaves `countryiso3code` empty on the income groups and Not classified (`XD`, `XM`, `XN`, `XT`, `XY`), and Global Economic Monitor rows (source 15) put the ISO3 code in `country.id` with `countryiso3code` empty, so `countryCode` takes the index's ISO2 and an empty `countryIso3` its three-character ID. A non-empty `countryiso3code` is kept as sent, and an entity the index does not carry keeps what upstream sent; `obs_status` → `obsStatus` (typically empty string; non-empty values signal data quality notes). `date` is a year, `YYYYQn`, or `YYYYMnn`. `dimension: { id, label }` appears on source-scoped rows from a source that has an extra dimension.
- `indicator: { id, name }` — echoed for chaining context
- `sourceScoped?: { sourceId, sourceName, dimension: { concept, selection, id, label } | null, note }` — present only when the source-scoped data API served the result. `selection` is `requested`, `only_value`, `world_total`, `newest_with_data`, `newest`, or `every_value` (then `id`/`label` are `null` and each row carries its own); `note` states that the values are not from the standard data endpoint and may be archived or superseded. `format()` renders all of it above the rows, and a row's own dimension value beside it whenever it differs from the applied one.
- `total: number`, `page: number`, `pages: number` — pagination state
- `nullCount: number` — count of null values in this page (helps the agent understand data sparsity)

`isAggregate: boolean` distinguishes regional/income-group entries from individual country entries so the agent can split the output if needed.

**Source-scoped path.** When the data endpoint answers message id `175`, the service looks the ID up in `/indicator/{id}` and queries its catalog source's `/v2/sources/{id}/...` data API, the live source first by the `preferredRow` tie-break. A named `dimension_value` routes to the first catalog source whose listing carries it, which is how an ID published under both Food Prices for Nutrition (`FPN 5.0`) and FPN Datahub Archive (`FPN 1.0`–`FPN 4.1`) reaches the archive without a source input. Every path segment is validated first: country codes against the source's `/country` listing (ISO2 and ISO3 are mapped through `/country`; a code no listing knows is `country_not_found`, a valid code the source doesn't publish is left out and named in the notice), the dimension value against its listing, and the periods from the source's `/time` listing. The series needs no request of its own: every catalog ID sits in its catalog source's series list. The dimension default depends on the concept:

| Concept | Default | Why |
|:--|:--|:--|
| any, with one value (PEFA `PUB`, Food Prices for Nutrition `FPN 5.0`) | that value (`only_value`) | nothing to choose |
| `Counterpart-Area` (International Debt Statistics: DSSI) | `WLD` (`world_total`) | the all-creditor total, and the counterpart the standard endpoint serves for IDS series (`DT.DOD.DECT.CD`, Angola 2020: identical values) |
| `Version` (WDI Database Archives) | the newest release holding any value for the requested countries and periods (`newest_with_data`), else the newest (`newest`) | a retired series carries only nulls in every later release |
| any other (ICP classifications, GDLD sectors, FPN Datahub Archive methodologies) | none — every value, each row labelled (`every_value`) | the values are different measures or breakdowns, not vintages of one |

`date_range` is expanded into the source's own time tokens that overlap the window, by the same overlap rule as the standard path, and sent as a `;` list (the API has no range syntax); a window covering every token sends no time segment, and one covering none returns an empty result without a request. `mrv` is applied locally, after the default release is resolved, because the API's own `mrv` picks periods across every value of an unpinned dimension: the N most recent periods holding any value across the requested scope, with every row at those periods, as the standard endpoint does. The whole scope is read (every upstream page) and sorted and paginated locally, so `total` and `pages` are the same on every page. A scope over 60,000 rows (countries × periods × unpinned dimension values) is `source_scope_too_large`.

**Errors:**
- `indicator_not_found` (`NotFound`) — indicator ID doesn't exist. Recovery: use `worldbank_search_indicators` to find valid IDs.
- `indicator_not_queryable` (`NotFound`) — the data endpoint doesn't serve the indicator and no catalog source can serve it through the source-scoped data API: the catalog no longer lists the ID, the catalog lookup failed, or the source is not organized by country, series, and time plus at most one dimension. Recovery: changing countries, dates, or `dimension_value` won't help; use `worldbank_search_indicators` to find another indicator for the same measure.
- `unknown_dimension_value` (`ValidationError`) — `dimension_value` is in no catalog source's listing for the ID. Thrown before any data request; the message lists every valid id per source and `validValues` carries them. Recovery: pass a listed id or omit `dimension_value`.
- `dimension_not_applicable` (`ValidationError`) — `dimension_value` given for an indicator the standard endpoint serves, or whose source has no extra dimension. Recovery: remove it.
- `source_scope_too_large` (`ValidationError`) — a source-scoped request would read more than 60,000 rows. Thrown before the data request, with `estimatedRows`. Recovery: narrow countries or `date_range`, or pin `dimension_value`; a narrower call reports the default it applied.
- `country_not_found` (`NotFound`) — one or more country codes are invalid. The message and `countryCodes` name the codes the country index lacks, as sent; `countries` carries the requested codes as an array. Recovery: use `worldbank_list_countries` to find valid codes.
- `indicator_and_country_not_found` (`NotFound`) — both the indicator ID and the country codes are invalid, the codes named the same way. Recovery: look both up before retrying.
- `mixed_all_selector` (`ValidationError`) — `countries` combines `"all"` with codes. Thrown before any request. Recovery: pass `"all"` alone, or list only the codes.
- `reversed_date_range` (`ValidationError`) — `date_range` is a well-shaped range whose first period comes after its second (`2020:2010`). Thrown before any request, after the `date_range`/`mrv` exclusivity check. Recovery: swap the periods.
- `multiple_indicators` (`ValidationError`) — `indicator_id` is `all`, refused in the handler: the data endpoint serves one indicator per call. Recovery: pass one ID found with `worldbank_search_indicators`.

The API answers `indicator_not_found`, `country_not_found`, and `indicator_and_country_not_found` with the same HTTP-200 `{"message": [{"id": "120", ...}]}` envelope and never names the parameter it rejected. It does emit one `message` entry per rejected path segment, so two entries prove both are bad; one entry is placed by a follow-up `/indicator/{id}` lookup, which is unambiguous by construction and costs a request only on a path that has already failed. Nor does it say which of several codes it rejected, so once the country segment is blamed, each requested code is looked up case-insensitively in the cached country index and only the codes it lacks are named (`KE;ZZ` names `ZZ`). The index places the blame without deciding it: it is read only after the rejection, never gating a call upstream accepts, and when it knows every code or fails to load, the whole list is named under the same reason. A cancellation during that read propagates as the caller's own.

Message id `175` ("The indicator was not found. It may have been deleted or archived.") is returned only after the country codes pass — a bad code on the same indicator produces the generic `120` and resolves as `country_not_found`. The id alone decides that the standard endpoint won't serve the indicator; the `/indicator/{id}` lookup then decides where the source-scoped path goes. If the lookup fails or lists nothing, the result is `indicator_not_queryable` rather than an unrelated upstream error.

Zero observations are not an error — the tool returns an empty array with an `enrichment.notice`, matching `worldbank_search_indicators`. The notice is chosen from `total`: zero gets the broaden-the-query wording (naming the window when upstream dropped it), and an empty page of a non-empty result gets the page-past-end notice naming the pages that exist at the served size. `total` and `pages` describe the filtered observations on every page, the ones past the end included.

### `worldbank_get_poverty`

Poverty and inequality estimates from the Poverty and Inequality Platform. The only tool backed by `PipService`.

**Input:**
- `countries: string | string[]` — one or more codes, or `"all"` for every economy. A single string may hold several codes separated by commas, semicolons, or pipes; all three are normalized to the comma-joined form PIP expects, so a caller carrying over `worldbank_get_data`'s semicolon habit is not silently wrong. At least one code is required. Codes resolve in one order:
  0. WDI's `IDA` (IDA total) and its ISO2 `XG` are `ambiguous_aggregate` before any request: PIP computes no IDA total, only its two parts, and the message names them as `IDX` and `IDB`.
  1. A two-character code resolves through the World Bank country index (`WorldBankApiService.lookupCountry`, the cache behind `isAggregate`) to its three-character ID — `NG` → `NGA`, `ZG` → `SSF`, `1W` → `WLD`. The index is read only when a two-character code is present; one it does not carry (`QQ`) is `country_not_found` before any PIP request.
  2. WDI's group spellings read as PIP's — `LMC`/`UMC` as `LMIC`/`UMIC`, `IDX`/`IDB`/`IBD` as `IDA`/`BLND`/`IBRD` — and duplicates collapse (`NG,NGA` is asked once). Every code handed back — a row's `countryCode`, the `appliedFilters.countries` echo, an error's message and `countryCodes` — names PIP's `IDA` as `IDX`, so a code copied from a response is accepted and asks for the same group, and that row's `countryName` is WDI's `IDA only` in place of PIP's bare `IDA`; PIP's other spellings (`LMIC`, `UMIC`, `BLND`, `IBRD`) are accepted as they come back.
  3. PIP's regions table (`/aux?table=regions`) routes aggregates to `/pip-grp`: `region`, `africa_split`, and `world` under `group_by=wb` (`group_by=world` answers HTTP 500, `wb` serves `WLD`), `incgroup` (`HIC`, `LIC`, `LMIC`, `UMIC`) and `ida` (`IDA`, `IBRD`, `BLND`, `REST`) under their own. The table's `fcv` and `regionpcn` codes (`FCVY`, `SSA`, `EAP`) and WDI's `MIC`/`LMY` are `unserved_aggregate`, whose list of accepted codes names PIP's `IDA` as `IDX`, and `welfare_type` or `reporting_level` beside any aggregate is `aggregate_filter_conflict`, both before any data request. Every other code goes to `/pip`. A regions table that fails to load degrades to an empty one — logged at warning, not cached — so every code goes to `/pip` as it did before aggregates were routed: an economy still answers, and an aggregate meets `/pip`'s 500 as `upstream_unavailable`.
  4. A `/pip` 404 on `country` is read against its own accepted list, which holds surveyed economies and aggregates only. A missing code PIP's full economy list (`/aux?table=country_list`) also lacks is `country_not_found`, naming just that code; the rest are economies PIP publishes only as model estimates (`CMD estimation` — 46 in release 20260922, e.g. `AFG`, `GUM`), answered from one `country=all&fill_gaps=true` request for the same year and filters, narrowed to them. With `fill_gaps: false` they return nothing and a notice says why.
- `year: string | undefined` — a four-digit year, `"all"` for full history, or `"MRV"` for the most recent available. Enforced by a schema `pattern`. Omitted behaves as `"all"`. Blank is read as absent, for form-based clients. The span a year must fall in is not checked here: it ends at the pinned release's last year (1963–2026 for 20260922, 1963–2025 for 20250930), and PIP's rejection names it. `MRV` follows `fill_gaps` (see the merge decision); an aggregate's `MRV` is resolved locally to its newest year, because `/pip-grp` answers `year=MRV` with `[]`.
- `poverty_line: number | undefined` — PPP dollars per person per day, 0–2700 (the range PIP itself enumerates). No server-side default: PIP's own default tracks the PPP vintage of the release it is serving, and the applied value comes back on every row as `povertyLine`.
- `welfare_type: 'income' | 'consumption' | undefined` — the two are not directly comparable, so a cross-country comparison is safer pinned to one. Rejected beside an aggregate.
- `reporting_level: 'national' | 'urban' | 'rural' | undefined` — ten economies publish a split, only China with all three levels; every row carries its own `reportingLevel`. Rejected beside an aggregate.
- `ppp_version: string | undefined` — a four-digit PPP vintage (`"2021"`, `"2017"`), shape-checked by the schema. It must be a vintage the newest release in `/versions` is published at; anything else is `ppp_version_unavailable`. Omitted resolves to that release's newest vintage. Blank is read as absent.
- `fill_gaps: boolean` (default: `true`) — economies only; `/pip-grp` ignores it.
- `page: number` (default: 1), `per_page: number` (default: 50, max: 1000) — applied locally over the merged economy and aggregate rows; PIP has no pagination. A page holds at most 70 estimates (see the output-budget decision); a larger size, the server default included, is reduced and `pages` is counted at the reduced size, with a notice when the result runs past one page.

**Output:**
- `estimates: Array<{ countryCode, countryName, regionCode, regionName, reportingYear, reportingLevel, welfareType, povertyLine, headcount, povertyGap, povertySeverity, watts, mean, median, gini, mld, polarization, decileShares, population, popInPoverty, surveyYear, surveyAcronym, surveyComparability, comparableSpell, estimationType, isInterpolated, isAggregate }>` — economies and aggregates in one list, ordered by code, year, reporting level, then welfare type.

An aggregate row (`isAggregate: true`) is what `/pip-grp` publishes: the poverty measures, `mean`, `population` (`reporting_pop`), and `popInPoverty`, with `estimationType` from its `estimate_type` — `actual`, `nowcast`, or `projection`. `/pip-grp` publishes no median, distributional block, survey fields, welfare type, reporting level, region, or interpolation flag, so those are `null` (`surveyAcronym` empty). `popInPoverty` is `null` on economy rows, which `/pip` publishes without it.

Every measure is nullable. `gini`, `mld`, `polarization`, `decileShares`, `surveyYear`, `surveyAcronym`, `surveyComparability`, and `comparableSpell` are populated only on survey-derived rows; `estimationType` (`survey` / `interpolation` / `extrapolation` / `CMD estimation`) is the field that says which kind of row this is. Across the full dataset the correspondence is exact: every `survey` row carries a `gini`, and no row of any other type does. `decileShares` is all ten shares or `null` — never a partial run, which would misreport which decile each share belongs to.

`surveyComparability` is PIP's series comparability code within an economy — 0 for its oldest comparable series, stepping up at each break — and `comparableSpell` the span of years that series covers. PIP sends both as `null` on gap-filled rows, and they pass through as `null`.

Enrichment carries `appliedFilters` (the codes as queried, the applied `fillGaps`, the resolved `pppVersion` and `releaseVersion`, the served `perPage`, and `requestedPerPage` when that was reduced), `totalCount`, `currentPage`, `totalPages`, and a `notice` when the result is empty, the page is past the end, the page size was reduced, the page contains gap-filled rows (with a pointer to `fill_gaps: false` when `MRV` resolved to an estimate year) or aggregate rows, or `fill_gaps: false` left a model-estimate-only economy out — composed into one string when more than one applies.

**Errors:**
- `country_not_found` (`NotFound`) — no economy or aggregate PIP publishes goes by the code, or a two-character code is not in the country index. The message names only the codes at fault, and a resolved one alongside the two-character code sent (`"1A" as ARB`). Recovery: look the code up, or use an aggregate code the `countries` description lists.
- `ambiguous_aggregate` (`ValidationError`) — WDI's `IDA` (IDA total) or its ISO2 `XG`. Thrown in the handler before any request; the message and recovery name `IDX` (IDA only) and `IDB` (IDA blend).
- `unserved_aggregate` (`ValidationError`) — an FCV or PovcalNet code from PIP's regions table, or WDI's `MIC`/`LMY`. Thrown before any data request; the message lists the accepted aggregate codes from the table (PIP's `IDA` as `IDX`) and `data.acceptedAggregates` carries them.
- `aggregate_filter_conflict` (`ValidationError`) — `welfare_type` or `reporting_level` beside an aggregate. Thrown before any data request.
- `invalid_parameter` (`ValidationError`) — PIP rejected some other parameter value. The message names it and quotes PIP's accepted values when they summarize to twelve entries or fewer (`year accepts all, MRV, 1963–2026`); `data.acceptedValues` carries the quoted lists. The recovery is chosen per throw: it points a parameter at the message's values only when the message lists them, and otherwise at the parameter's own description.
- `ppp_version_unavailable` (`ValidationError`) — `ppp_version` is not a vintage of PIP's current release. Thrown before any `/pip` request; the message names the release and the vintages it offers.
- `upstream_unavailable` (`ServiceUnavailable`) — a 5xx. The body carries no detail, so the message states the status; aggregate codes, which `/pip` answers with a 500, never reach it. A country index that fails to load while resolving an ISO2 code is `upstream_unavailable` too, before any PIP request: the message names the Indicators API country listing, `status` is forwarded when there was one, and the recovery adds that ISO3 codes need no lookup. A cancellation of the call during that load propagates as the caller's own.

PIP answers a rejected parameter with a real HTTP 404 whose body names the parameter and enumerates every accepted value. The framework's default error-body capture is 500 bytes, which cuts even a lone `year` rejection (635 B), so `PipService` raises it to 8 KiB — the largest body measured is 2,221 B, four parameters with `country` among them — and parses the body. Each `valid` list is summarized in PIP's order, collapsing a run of three or more whole numbers that step by one into a range; a gap ends the run, so a non-consecutive list is never shown as a span. A rejected `version` answers with an unkeyed `details: {msg, valid}` that names no parameter, and is reported as a rejection of an unnamed one. A body that still fails to parse falls back to matching the `"<name>": {"msg"` prefixes for the names alone, with no values quoted. Zero rows is a successful empty result with a notice, not an error — PIP returns `[]` for a well-formed query that matches nothing.

### `worldbank_search_projects`

The World Bank lending portfolio — 28,074 operations as of 2026-08-09. The only tool backed by `ProjectsService`.

**Input:**
- `query: string | undefined` — free text over project names, abstracts, and objectives. Terms combine as AND, so extra words narrow. Blank is read as absent. The API parses it with a Lucene-style grammar and answers what it cannot parse with HTTP 400: brackets or braces, an unmatched `"`, a `/` between words, a trailing `\`, an AND or OR at either end, and a trailing NOT (`water [`, `[water]`, `"water`, `water OR`, `AND water`, `water NOT`). A balanced quoted phrase, AND/OR between words, a leading `-`, and a leading NOT all parse, though a query of excluded terms alone (`NOT water`, `-water`) matches nothing. The grammar is not pre-validated — the 400 is classified instead — except for `#`, which the API answers with HTTP 200, `total: "undefined"`, and rows unrelated to the search, so a `query` containing `#` is rejected in the handler before any request.
- `countries: string | string[] | undefined` — ISO3, ISO2, or World Bank regional codes, single, array, or one string separated by commas, semicolons, or pipes. The API keys on a two-character code, so every code is resolved to the one the portfolio uses before the request. A blank value (`""`, `[]`, `[""]`) reads as no country filter, for form-based clients, but a non-blank value that splits to no codes (`","`, `"|"`, `["|"]`) is `invalid_country_code`: sent on as no filter it would search the whole portfolio. The handler then rejects any code that isn't two or three alphanumeric characters after the split, before any request. A three-character code then resolves through `WorldBankApiService.lookupCountry` (the cached country index `worldbank_get_poverty` also reads) to its ISO2 code; the index is read only when such a code is present, so a search in two-character codes never touches the Indicators API. An unknown three-character code and a WDI aggregate (`SSF`, `WLD`, `SAS`) are `invalid_country_code`. Last, one table (`src/services/projects/portfolio-country-codes.ts`) maps the four economies the portfolio files under legacy codes — Yemen `YE` → `RY`, DR Congo `CD` → `ZR`, West Bank and Gaza `PS` → `GZ`, Timor-Leste `TL` → `TP` — whether they arrived as ISO3 or ISO2; the legacy code itself is accepted as sent. Codes are uppercased and deduplicated, and `appliedFilters.countries` echoes them as sent upstream. Digits are accepted because 34 of the 218 codes the portfolio uses are World Bank regional codes (`3A`, `4E`, `1W`) rather than ISO2.
- `status: Array<'Active' | 'Closed' | 'Dropped' | 'Pipeline'> | undefined` — the complete set the portfolio publishes, read off the endpoint's own facet.
- `region: string[] | undefined` — the nine World Bank operational regions, likewise read off the facet. These are lending regions, not the WDI aggregate codes `worldbank_get_data` accepts.
- `financial_type: Array<'IBRD' | 'IDA' | 'Grants' | 'Other'> | undefined` — financing windows, combined as OR and sent as `projectfinancialtype_exact` joined with `^`. The four values are the complete vocabulary (a sweep of all 28,153 projects, 2026-09-25), case-sensitive upstream, and exactly what `financialTypes` reports. A project publishing no window — 10,033 of 28,153 — never matches. The `Grants` window is a financing classification, not the `grantAmount` figure.
- `approved_from` / `approved_to: string | undefined` — inclusive board-approval window as `YYYY-MM-DD`. The shape is a schema `pattern`; that the date exists (month 01–12, day within the month, February 29 only in a leap year) and that `approved_from <= approved_to` are checked in the handler, before any request, as `invalid_date` and `reversed_date_range`. Blank is read as absent.
- `include_abstract: boolean` (default: `false`) — an abstract longer than 5,000 characters (`MAX_ABSTRACT_CHARS`) is cut there and marked with `…` on both surfaces, and `notice` names the projects cut; `url` leads to the full text.
- `page: number` (default: 1), `per_page: number` (default: 50, max: 1000) — translated to the API's `os` (skip) and `rows`. A page holds at most 80 projects, or 8 with `include_abstract` (see the output-budget decision); a larger size, the server default included, is reduced, with a notice when the result runs past one page, and both `os` and `pages` use the reduced size.

**Output:**
- `projects: Array<{ id, name, status, countryCodes, countryName, regionName, boardApprovalDate, closingDate, totalCommitment, ibrdCommitment, idaCommitment, grantAmount, financialTypes, majorSectors, abstract, url }>` — newest board approval first, nulls last, with or without `query`, and the order pagination walks. Every request sends `srt=boardapprovaldate&order=desc`: without `qterm` that is upstream's default anyway, but with `qterm` upstream orders by descending project ID, which left the newest approvals pages deep.

Coverage is uneven across a portfolio reaching back to 1947. Across all 28,074 records only `id`, `project_name`, `status`, `countryname`, `countrycode`, and `regionname` are present on every row; `boardapprovaldate` is absent on 2%, `major_sectors` on 17%, `projectfinancialtype` on 36%, `closingdate` on 44%, and `project_abstract` on 48%, so those are nullable. Dropped operations account for most of the gaps — 2% of them publish a closing date, against 89% of active ones. `countrycode` is a list upstream but holds exactly one code on every record, regional operations included; `countryCodes` reports the four legacy portfolio codes as their WDI ISO2 (`RY` → `YE`, `ZR` → `CD`, `GZ` → `PS`, `TP` → `TL`) so a code chains into the Indicators tools, and passes every other code through. `boardApprovalDate` is narrowed from the upstream timestamp to the calendar day the tool's own date filters use. `financialTypes` and `majorSectors` are deduplicated — upstream repeats a financing window once per instrument and a major sector once per sector rolling up to it. `url` is derived from the ID; the API publishes no link field.

The amounts follow the project page. `totalCommitment` is `curr_total_commitment`, the page's "Commitment Amount"; across all 28,153 records (2026-09-25) it equals `totalamt` + `grantamt` on every row that carries it, and it is absent on 35.8%, against 51.4% for `totalamt`. `ibrdCommitment` and `idaCommitment` are `curr_ibrd_commitment` and `curr_ida_commitment`, which sum to `totalamt` (IDA grants included), and `grantAmount` is `grantamt`. `grantamt` is not only World Bank money: on 3,124 of the 7,258 rows where it changes the total it includes other agencies' co-financing recorded on the operation (P510631's 270,000,000 is Asian Development Bank and AIIB lending), so World Bank lending alone is `ibrdCommitment` + `idaCommitment`. `grantAmount` is also unrelated to the `Grants` financing window in `financialTypes`. Every missing amount is `null` rather than `0`, and the four only sum within float32 precision on some rows, so nothing downstream should assume an exact identity. The project page labels these "Commitment Amount", "IBRD + IDA Commitment", and "Grant Amount"; `lendinginstr` is published on no record, so no financing instrument is reported.

`format()` renders six lines a project: the heading, status with country and region, the two dates, the commitment line, sectors, and the URL, plus an abstract line only when the row carries one — `include_abstract` in the applied-filters trailer says whether abstracts were requested. The commitment line names only the parts that add to the total: null and zero parts are left out, and so is a single remaining part equal to the total. `structuredContent` rows carry every field as normalized, nulls and zeros included.

Enrichment carries `appliedFilters` (including `includeAbstract`, the served `perPage`, and `requestedPerPage` when that was reduced), `totalCount`, `currentPage`, `totalPages`, and a `notice` for an empty result, a page past the end, a reduced page size, or abstracts cut at the ceiling.

**Errors:**
- `invalid_country_code` (`ValidationError`) — `countries` holds only separators, a `countries` entry is not two or three alphanumeric characters (both checked ahead of the date checks, before any request), no economy in the country index has that three-character code, or it is a WDI aggregate. Thrown before any Projects request, with the offending codes in `invalidCodes`. The message separates an unknown code from an aggregate. Recovery: an ISO3 or ISO2 economy code from `worldbank_list_countries`, a regional code for multi-country operations, or the `region` filter in place of an aggregate.
- `invalid_date` (`ValidationError`) — `approved_from` or `approved_to` is shaped `YYYY-MM-DD` but names no real day. Thrown before any request. Upstream answers an out-of-range month with HTTP 500 and silently accepts an out-of-range day, so neither may reach it.
- `reversed_date_range` (`ValidationError`) — `approved_from` is after `approved_to`. Thrown before any request; upstream would answer with a plain zero-hit.
- `page_out_of_range` (`ValidationError`) — the requested page starts past the 100,000-result offset the API serves, at the served page size. Thrown before any request.
- `invalid_query` (`ValidationError`, not retryable) — an HTTP 400 on a request carrying `qterm`, or a `query` containing `#`, rejected before any request. Every other filter is validated before the request, so a 400 with `qterm` present is the query failing to parse. The message says so and quotes the query; the contract recovery names the syntax to remove.
- `upstream_unavailable` (`ServiceUnavailable`) — every other non-success status, or an HTML error page. Retried where the framework's own classification of the status is transient — 429, 408, and 5xx other than 501 — with an upstream `Retry-After` forwarded so the retry honors it, and marked not retryable where it is not (403, 404, 501, a 400 with no query). The recovery is the contract's: retry once. A country index that fails to load while resolving an ISO3 code is `upstream_unavailable` too, before any Projects request: the message names the Indicators API country listing, `status` is forwarded when there was one, and the recovery adds that ISO2 codes need no lookup. A cancellation of the call during that load propagates as the caller's own.

Every filter is an exact match upstream and an unmatched value is HTTP 200 with `total: 0` — the same response a genuine no-match produces. The schema and handler close that hole everywhere they can: `status` and `region` are enums, the dates are checked as real, ordered calendar days, `per_page` is capped, and multi-value filters are joined with `^` by the service rather than the comma a caller would reach for, which upstream reads as part of a single value. Country codes are the one filter a schema cannot settle — two characters is well-formed, and only the index knows whether the portfolio has ever used them — so an empty result with a country filter in force costs one extra `rows=0` request asking the country filter alone. Zero there means no project carries any of the codes; a positive count means they match as a set and the notice names the other filters as the cause, adding that with more than one code in force the count does not clear each of them individually. A probe that fails is swallowed: the search itself succeeded, so the empty result is returned with the generic notice rather than turned into an error.

## Design Decisions

| Decision | Rationale |
|:---------|:----------|
| Single `worldbank_get_data` for all data queries | The API returns data in the same shape regardless of whether you query one country, many, a region, or `all`. Splitting by use case would be a 1:1 API-mirror mistake — the tool is already self-sufficient with flexible `countries` input. |
| `countries` accepts both single string and array | Agents most often query 2–6 countries for comparison; array input reads naturally for that case. The service layer joins the array with `;` before calling the API. |
| `include_aggregates` defaults to `false` in `worldbank_list_countries` | Aggregate entries (regions, income groups) look like real countries in the raw API response and confuse country-browsing workflows. A researcher asking "list Sub-Saharan countries" doesn't want `AFR`, `AFE`, `SSA` in the results. Aggregates are fully accessible by setting the flag or querying with aggregate codes directly. |
| Aggregate-free country listing fetches every upstream page | The API has no server-side aggregate filter, so `include_aggregates=false` must filter locally — and can only do that correctly over the complete entity set. A fixed first-page fetch made anything past that page unreachable and made `total`/`pages` under-report silently. `include_aggregates=true` still pages straight through to upstream, except under `lending_type`, whose doubled rows only a deduplicated local page can count. |
| `isAggregate` field on data rows | The WDI mixes individual country data with regional aggregates in `all` queries. The agent needs to split or label them correctly for analysis. The data endpoint carries no `region`/`incomeLevel` field, so the flag is a lookup against the aggregate codes derived from `/country` — the same `region.id = "NA"` rule the country tools apply, which keeps all three in agreement by construction. |
| `mrv` vs `date_range` as mutually exclusive | The API supports both `mrv` and `date` independently. They serve different workflows (explore recent trends vs. historical analysis) and combining them yields confusing results. Making them mutually exclusive in the schema forces clarity. |
| All keyword matching is client-side over an exhaustively fetched scope | `?searchterm=` never filters, so there is no server-side search to lean on for any query shape. Every keyword path fetches its whole scope (catalog, topic, or source) by looping the envelope's `pages`, then matches and paginates locally. A single-shot fetch with a fixed page size would silently drop matches past that page. |
| Full-catalog fetch is cached in-process with single-flight | The catalog is ~15 MB / 29.5k rows and paying that on every keyword-only search is untenable. A TTL'd cache on the service instance (`WORLDBANK_CATALOG_CACHE_TTL_MS`, default 1 h) with a shared in-flight promise keeps concurrent searches to one fetch. State lives on the instance, not module scope, so tests and multiple instances stay isolated. |
| Token-AND matching on alphanumeric terms, ranked by specificity | Whole-string substring matching is word-order sensitive: "per capita GDP" returned 8 hits where "gdp per capita" returned 38, for the same intent. Requiring each term independently makes both return the same 108. Splitting on punctuation rather than whitespace is what keeps a copied indicator name working — `Unemployment, female (%)` tokenized on whitespace yields `(%)`, which appears in no name, and the query returns nothing. The looser tokens widen recall, so the ranking tiers do the work of putting the obvious answer first: exact, starts-with, whole-phrase, whole-word, then the rest. Within a tier, World Development Indicators leads, then other live sources, then archives, because catalog order put a regional dataset's `6.0.GDPpc_constant` first for `GDP per capita` and the archived `EN.ATM.CO2E.PC` first for `CO2 emissions per capita`; and a series leads its own breakdowns, because the catalog lists `EG.ELC.ACCS.RU.ZS` (rural) ahead of `EG.ELC.ACCS.ZS` for `access to electricity`. |
| Duplicate indicator IDs collapse to one row, the archived source dropped | An exhaustively fetched catalog carries 54 IDs twice from two unrelated causes: 43 are the same indicator published under a live source and an archived copy of it, and 11 are single rows that repeat because `/indicator` is not stably ordered between page requests, so a row can land on both sides of a page boundary. Returned as-is they read as distinct indicators, so an agent chains both into `worldbank_get_data` and issues duplicate requests for one series, and `total` counts both rows. Collapsing the fetched pool rather than the catalog is what covers both causes. Keyword search collapses before ranking: the row whose source name contains "Archive" loses, and a tie falls to the lower source ID, so the survivor never depends on the order upstream returned the rows in. `worldbank_get_indicator` applies the same tie-break — `/indicator/{id}` returns the archived row first, so taking the first row reported a different source than search did for the same ID. |
| Empty results are structured success, not `no_match` | A search with zero hits is a valid answer. It returns an empty array plus an `enrichment.notice` carrying the recovery hint, matching `worldbank_get_data`'s empty-result handling. The declared `no_match` error was unreachable and was removed rather than wired up. |
| No `worldbank_compare_countries` workflow tool | A first-class comparison tool is tempting but adds no real value over `worldbank_get_data` with multiple countries — the agent can do the comparison logic. Keeping the surface tight avoids duplicating the data query with a thin wrapper. |
| DataCanvas not used | Data result sets are moderate-sized (200 countries × N years). The 200-row served page and typical query sizes (10–50 rows for focused country comparisons) don't warrant the DuckDB overhead. An agent doing deep tabular analysis can call multiple times. This can be revisited if large `all`-country time-series queries prove problematic in practice. |
| One `worldbank_get_poverty`, not a separate `worldbank_get_inequality` | PIP returns the poverty measures and the whole distributional block in the same row, and `poverty_line` does not affect the inequality fields — a second tool would fire an identical upstream request for data the first call already had in hand. The tool-selection cost of hiding "Gini" inside a tool named `get_poverty` is paid in prose: the description names Gini, inequality, and decile distribution explicitly so a search for those concepts lands here. |
| `fill_gaps` defaults to `true`, and the applied value is echoed | Upstream defaults it to `false`, where an ordinary query (`country=IND&year=2019`) returns a bare `[]` rather than an error, because India has no 2019 survey. Defaulting to `true` makes the common query answerable. It is echoed in `appliedFilters` because an agent cannot reason about a fallback it cannot see. |
| Survey rows are fetched first and the gap-fill pass only adds what they left uncovered | `fill_gaps=true` is not a superset of `fill_gaps=false`: PIP strips `gini`, `mld`, `polarization`, the ten deciles, and `survey_year` from **every** row it returns in that mode, including rows for years a survey does exist for (`USA&year=2022` returns `gini: 0.417` without the flag and `gini: null` with it). A single request using the caller's `fill_gaps` value would therefore leave the entire inequality half of this tool permanently null. Asking for survey rows first and merging the gap-filled pass around them keeps the real distribution wherever one exists. What counts as uncovered depends on the request: a four-digit year is answered per economy — PIP returns the same row grain in both modes for a year it surveyed, so an economy with a survey row needs nothing added. A request spanning the window (`all`, or no `year`) is answered per row grain, because PIP surveys a handful of years and estimates every year around them. `MRV` runs both passes, keys the merge on row grain, and keeps each economy's newest year, so it follows `fill_gaps` the way PIP's own `MRV` does and never returns one economy at two years. |
| Provenance is a first-class output field, not an inference | Gap-filled rows are the common case, since PIP publishes an estimate for nearly every year and surveys only a handful. `estimationType`, `surveyYear`, `surveyAcronym`, and `isInterpolated` ship on every row, and `.describe()` states that null inequality on a gap-filled row is a documented data gap, so an agent can tell "no data for this year" from "this year is an estimate that carries no distributional detail." `isInterpolated` alone is not enough — it is `true` on interpolated and extrapolated rows but `false` on `CMD estimation` rows, which are gap-filled all the same. |
| No server-side default for `poverty_line` | PIP's own default tracks the PPP vintage of the release it serves, which has already moved once ($2.15 under 2017 PPPs, $3.00 under 2021 PPPs). Pinning a number here would silently express the applied line in the wrong vintage after the next revision. The line PIP applied comes back on every row as `povertyLine`. |
| `PipService` is a separate service, not an extension of `WorldBankApiService` | Nothing transfers: `buildUrl()` forces `format=json` plus `page`/`per_page`, which PIP takes neither of; `fetchAllPages()` assumes the `[paging, items]` tuple, where PIP returns a flat array; `isWbErrorEnvelope()` detects an HTTP-200 sentinel, where PIP uses real status codes. The reuse is one level down — `fetchWithTimeout`, `withRetry`, the init/accessor pattern, and HTML-error detection against the shared Cloudflare front. |
| PIP's 5xx retry budget is one retry, not the framework default of three | Some query shapes fail with HTTP 500 on every attempt (`country=all&year=all&povline=4.11&welfare_type=consumption`, measured 2026-09-25), so extra retries only delay a settled answer. The one retry is kept for the timeout case instead: PIP computes a query on first sight and caches it, so the attempt that timed out warms the query and the retry usually returns at once. The 500 body carries nothing but `Internal Server Error`, so the message states the status. The aggregate codes that used to cause it on `/pip` now route to `/pip-grp` before any request. |
| Resources for country and indicator | Stable, addressable by ID, read-only, useful as injectable context for agents that support resources. Both entities satisfy the resource criteria without redundancy — their tool path (`worldbank_get_country`, `worldbank_get_indicator`) also covers tool-only clients. |
| `worldbank_search_projects` filters are enum-backed wherever the value set is closed | Every filter on this endpoint is an exact match, and an unmatched value returns HTTP 200 with `total: 0` — indistinguishable from a real no-match. `status` has four values, `region` nine, and `financial_type` four, all enumerable from the endpoint's own data, so a Zod enum makes a typo unreachable rather than something the agent has to diagnose from an empty result. The same reasoning rejects an impossible or reversed board-approval window before the request. |
| Multi-value filters are joined with `^`, and the tool splits commas itself | The API's list separator is a caret. A comma reads as part of one value — `countrycode_exact=BR,IN` returns `total: 0`, the silent-zero shape again — and region names contain commas of their own, so a comma-joined list could not express them at all. The tool accepts the comma-, semicolon-, and pipe-separated input its sibling tools take and the service converts, so the separator never becomes the caller's problem. |
| An empty result probes the country filter in isolation | Client-side validation closes every filter with a knowable value set, which leaves country codes: two characters is well-formed and only the index knows whether the portfolio uses them. One extra `rows=0` request asking `countrycode_exact` alone separates "no project carries this code" from "the codes are fine and the other filters emptied the result", and the notice says which. The probe asks the codes as one OR-set, so a positive count settles the set and not each member; the notice says so when more than one code is in force, rather than paying one request per code. Its failure is swallowed — the primary search already succeeded, and a broken diagnostic must not turn a valid empty result into an error. Facets cannot do this job — they are scoped to the query, so a zero-hit response carries an empty `facets` object. |
| Countries take ISO3 or ISO2 and are resolved to the portfolio's own code before the request; WDI aggregates are rejected as `invalid_country_code` | The Projects API keys on a two-character code (`BR`); `countrycode_exact=BRA` returns `total: 0`, and every other tool trains the agent on ISO3. Rejecting ISO3 cost a round trip on the likeliest mistake, so a three-character code resolves through the cached country index instead, read only when one is present. ISO2 is not the whole story: the portfolio files Yemen, DR Congo, West Bank and Gaza, and Timor-Leste under `RY`, `ZR`, `GZ`, and `TP`, so their ISO2 codes matched nothing and the notice blamed a missing lending history. One table maps them on input from either identifier and back to WDI ISO2 on output, so `countryCodes` chains into the Indicators tools. Aggregates stay rejected: the ISO2 codes of `WLD`, `EAP`, `ECA`, and `SAS` (`1W`, `4E`, `7E`, `8S`) are regional codes selecting multi-country operations only (`8S` 18 against 2,371 for `region: South Asia`), and `worldbank_get_poverty` accepts aggregates only because PIP computes them. The shape check keeps digits: 34 of the 218 codes in use are World Bank regional codes (`3A`, `4E`, `1W`), and a letters-only rule would make 1,078 multi-country operations unreachable (2026-09-25). |
| `include_abstract` defaults to false | Abstracts are the single largest component of the payload — a median of roughly 1,200 characters, a p90 of 2,300, a max of 8,000, and a measured 111 KB for a default 50-row page against 53 KB without them. They arrive whatever `fl` asks for, so the choice is only whether to emit them, and a search tool is usually being used to narrow rather than to read. The flag is echoed in `appliedFilters` so a `null` abstract is never ambiguous between "not requested" and "none published". |
| The page size is clamped in the service, not just the schema | Upstream accepts `rows=5000`, echoes `"rows": 5000` back in the envelope, and returns 1,000 records. Nothing but counting the body reveals the truncation, so the ceiling is enforced before the request and `pages` is computed against the clamped size. The output-budget caps (80, or 8 with abstracts) sit below that ceiling and are applied at the same point. |
| Large pages are capped per request shape and disclosed, not rejected | `per_page: 1000` produced 2.07 MB of text with abstracts and 0.52 MB without on `worldbank_search_projects`, and 0.57 MB on `worldbank_get_poverty`. The schema maximum stays at 1,000 so existing callers get a smaller page with a notice rather than an error; the served size is echoed as `appliedFilters.perPage` beside `requestedPerPage`. The notice is left off when the whole result fits on one page at the served size: that page is the one the requested size would have served, so there is no reduction the caller could notice, and the echo alone records it. The cap is fixed per shape rather than fitted to each page's rows, because only a fixed size keeps `(page - 1) × size` contiguous — both for a caller following the echo and for one that keeps sending 1,000. The same mechanism covers `worldbank_get_data` (200 observations) and `worldbank_list_countries` (150 entries). Where rows vary too much for a useful cap, the long field is shortened instead and the page keeps its size: `worldbank_search_indicators` returns a 150-character `sourceNote` excerpt, and an abstract on `worldbank_search_projects` is cut at 5,000 characters, disclosed in `notice`. The 8-row abstract cap alone left a reachable page at 68,985 B, and a smaller cap would reject calls existing clients make; 98% of published abstracts are untouched and the project page carries the rest. |
| Recoverable input mistakes are rejected in the handler; shape stays on the schema | A schema refinement rejects with `InvalidParams` and no `reason` or recovery hint, and a `.refine()` does not appear in the advertised `inputSchema` either. A well-shaped value a caller corrects and retries therefore carries a declared reason: `worldbank_search_projects`' country code that resolves to no economy, impossible date, reversed window, and `#` in `query`, and `worldbank_get_data`'s reversed `date_range` and `"all"` mixed with codes. What the schema keeps is shape — the date and period patterns, identifier patterns, numeric bounds advertised as `minimum`/`maximum`, enums — and an empty `countries` value, which is a missing required input rather than a mistake with a correction to suggest. |
| Every `/pip` request of one query carries the same fully-qualified `version` | The survey pass and the gap-fill pass are two requests; pinning both to one resolved `version` means a release rolling between them cannot mix vintages in one result. Resolution is confined to the newest release in `/versions`, because `/pip` answers HTTP 500 for the older releases the listing still carries. |
| Upstream error bodies are never quoted into a message | A 4xx body carries the hostname and index name of the search cluster behind the API; a 5xx body carries a Node stack trace with absolute paths from the upstream host. Neither helps an agent, and both are the API's internals. The message states the status and nothing else, with the original kept as the error's `cause`. |

## Known Limitations

- **Search is literal substring matching.** No semantic search, no stemming, no fuzzy matching. An agent searching for "income inequality" won't find the Gini coefficient unless it also tries "Gini". Synonyms require multiple calls. Short terms match inside longer words (`us` hits `housing`); the whole-word tier ranks those hits below ones where every term stands as a word, but still returns them.
- **Search results carry a description excerpt.** `worldbank_search_indicators` returns the first 150 characters of each `sourceNote`; the whole note is matched against, and `worldbank_get_indicator` returns it.
- **Data sparsity is inherent.** Many indicators lack data for specific countries or years — the API returns `null` for those cells without warning. `nullCount` in the response quantifies this; the agent must interpret null values in context.
- **The upstream `searchterm` parameter does not filter.** It is accepted and ignored — a nonsense term still returns the full 29,500-record catalog with the same `total`. There is no server-side full-text search to fall back on, so the service does all keyword matching itself.
- **A keyword-only search costs a full-catalog fetch on a cold cache.** ~15 MB and a few seconds, once per `WORLDBANK_CATALOG_CACHE_TTL_MS` window per process. Topic- and source-scoped searches are far smaller (the largest source is ~1,500 rows).
- **The catalog contains duplicate indicator IDs.** 43 IDs are published twice in `/indicator`, once under a live source and once under an archived copy of it. Keyword search collapses them to one row per ID and `worldbank_get_indicator` resolves to the same row, so the extra copy's `sourceId`/`sourceName` is not reachable through either path. The no-keyword browse paths page straight through upstream without collapsing, which they can do because the pairs differ only by source: a source-scoped listing filters server-side on that field, and every one of the 43 carries an empty `topics` array, so no topic-scoped listing contains a pair either.
- **1,887 catalogued indicator IDs are served only by the source-scoped data API.** The data endpoint rejects them with message id `175`, and neither a country/date scope nor a `source` parameter changes that. Sampled across every catalog source on 2026-09-12, the rejection tracks the source's layout exactly: every source with a fourth concept beyond Country/Series/Time is rejected (WDI Database Archives 1,016 IDs, International Debt Statistics: DSSI 532, PEFA 2016 129, ICP 2017 47, the 43 Food Prices for Nutrition / FPN Datahub Archive pairs, PEFA CRPFM 43, ICP 2005 36, PEFA GRPFM 21, GDLD 16, PEFA 2011 4), and every three-concept source is served. `worldbank_get_data` answers them through the source-scoped path; `worldbank_search_indicators` and `worldbank_get_indicator` return them without marking them.
- **Source-scoped queries read their whole scope.** The API's row order changes with the request, and the WDI Database Archives default release can only be found from the data (the API's own `mrv` would pick periods across every release before it is known), so each call reads every row in scope and applies `mrv` and pagination locally. A cold process's first call to a source with an extra dimension spends eight requests (the standard rejection, the catalog lookup, the `/country` index, the source's concepts and its dimension, country, and time listings, then the data), plus one per further 10,000-row page of data; once the listings are cached, three. The default release costs a read across all 139 releases: one country over all years is 9,313 rows, every country for one year 40,588 rows (~12 MB, about 7 s). Past 60,000 rows the call is refused; pinning `dimension_value` divides the scope by 139.
- **A WDI Database Archives release can be null for a whole series.** Rows exist for every release, country, and year whether or not the release carried the series, so a pinned release the series was absent from returns only nulls. The default avoids this by taking the newest release holding a value in scope.
- **Indicator IDs are opaque and hierarchical.** IDs like `NY.GDP.PCAP.CD` encode source, topic, and unit, but the encoding isn't documented for programmatic parsing. The agent should treat them as opaque strings.
- **PIP inequality data exists only for survey years.** PIP publishes a poverty estimate for every year from 1981 to 2026 in an economy's coverage window but surveys only a handful — 2,584 survey rows against 10,119 gap-filled ones across the whole dataset — and it attaches the Gini, decile shares, mean log deviation, and polarization to survey-derived rows alone. For most year requests the inequality fields are legitimately null. `estimationType` distinguishes that from an outright absence of data.
- **PIP's aggregates carry no distribution and follow a lagging income classification.** `/pip-grp` publishes poverty measures, mean, population, and people in poverty for each aggregate, but no median, Gini, deciles, welfare type, or reporting level. Income groups use the classification PIP's release was built with in every year — FY2026 (July 2025) for release 20260922, which differs from the current WDI classification for 7 economies (PHL, VNM, JOR, LKA, FSM, TGO, VEN) — and PIP's `IDA` is IDA-only (WDI `IDX`, 59 economies), so WDI's IDA total has no PIP aggregate and is rejected. FCV and PovcalNet groupings are served upstream under their own `group_by` but not routed here.
- **A model-estimate-only economy costs the all-economy response.** `/pip` rejects the 46 economies PIP publishes only as model estimates by code, so they are read from `country=all`: ~190 KB for one year, 8.9 MB for `year: "all"` (2.9–4.0 s cold, 0.2–0.6 s warm, parsed in 12–33 ms, measured 2026-09-25). No lighter upstream route exists — per-year requests would be 46 × 190 KB — and surveyed economies never take this path. A failure of that request names the economies it was read for, not `all`.
- **PIP and WDI poverty figures will not match exactly.** `SI.POV.DDAY` and friends are WDI series with their own vintage and revision cycle; `worldbank_get_poverty` reads PIP directly. Comparable questions, different numbers.
- **A cold PIP query is slow.** PIP computes a query the first time it sees it and serves repeats from cache, so the same request can take 15–60 seconds once and under a second thereafter; 90 seconds has been observed. The request timeout is 60s with a single retry, which recovers the common case because the timed-out attempt leaves the query warm. A full-history request with `fill_gaps` on pays this twice, once per pass.
- **Update frequency varies widely.** Some indicators are annual, some quarterly, some have multi-year gaps. The API provides no update schedule — agents querying "most recent data" may get values from several years ago.
- **The Projects API ignores a parameter it does not recognize.** A misspelled filter name is dropped and the search runs unfiltered, returning the full 28,074-project total as though the filter had been satisfied. The tool sends only the parameters it knows, so this is unreachable through it, but it rules out ever passing caller-supplied parameter names through.
- **Several documented-looking Projects filters do nothing.** `borrower_exact`, `impagency_exact`, and `teamleadname_exact` appear in the field list the endpoint advertises via `fl=*`, and `lendinginstr_exact`, `fiscalyear_exact`, and `majorsector_exact` are the obvious names for filters the data supports — all six are accepted and ignored, leaving the total unchanged. Only the filters the tool exposes were confirmed to narrow a result.
- **Projects coverage thins going back in time.** 44% of the portfolio publishes no closing date, 36% no commitment amount, and 48% no abstract; the oldest operations carry little beyond an ID, a name, a country, and a board date, and 2% carry no board date either. A `null` amount is missing data, not a commitment of zero.
- **Projects sector data is not on one vintage.** Older operations carry sector and theme names prefixed `FY17 - `, newer ones carry unprefixed names for the same concepts. `majorSectors` reports what the record holds; matching sectors across eras needs the agent to account for the prefix.
- **The Projects portfolio is mostly history.** 18,293 of 28,074 operations are closed and 6,901 were dropped, against 2,581 active and 299 in the pipeline. A search with no `status` filter is dominated by finished lending.

## API Reference

**Base URL:** `https://api.worldbank.org/v2/`

**Format:** Always append `?format=json`. Without it, the API returns XML.

**Response envelope:** `[{page, pages, per_page, total}, [...items]]` — a two-element JSON array, not an object. The data endpoint envelope includes two additional fields: `sourceid` (source dataset ID) and `lastupdated` (last data update date).

**Error envelope:** Invalid IDs (indicator, country) return HTTP 200 with a message object instead of a 404: `{"message": [{"id": "120", "key": "Invalid value", "value": "The provided parameter value is not valid"}]}`. The service layer must detect this shape and map it to `NotFound`. The data endpoint also returns `{"id": "175", "key": "Invalid format", "value": "The indicator was not found. It may have been deleted or archived."}` for a catalogued indicator it does not serve.

**Pagination:** `?page=N&per_page=N`. Default per_page varies by endpoint (typically 50). Max per_page for data endpoint: 1000. Indicator listing has no fixed cap.

**Country codes:**
- ISO2 (2-letter, most common): `US`, `CN`, `DE`
- ISO3 (3-letter): `USA`, `CHN`, `DEU`
- Region codes (`region.id` on the countries endpoint — not its `iso2code`, which is `ZQ` for `MEA`): `EAS` (East Asia & Pacific), `ECS` (Europe & Central Asia), `LCN` (Latin America & Caribbean), `MEA` (Middle East, North Africa, Afghanistan & Pakistan), `SAS` (South Asia), `SSF` (Sub-Saharan Africa), `NAC` (North America). `/v2/region` lists 43 codes in all; `?region=` on `/country` accepts every one, the rest filtering by membership (`AFE`, `AFW`, `ARB`, `EUU`, `LDC`).
- Lending types (`lendingType.id`): `IBD` (IBRD), `IDB` (Blend), `IDX` (IDA), `LNX` (Not classified); `?lendingType=` filters on them and answers the first three with every entry twice
- Income groups: `HIC` (High income), `UMC` (Upper middle income), `LMC` (Lower middle income), `LIC` (Low income)
- Special: `WLD` (World), `1W` (alias for World), `all` (all entries)

**Key indicator IDs (reference):**

| Indicator | ID |
|:----------|:---|
| GDP (current US$) | `NY.GDP.MKTP.CD` |
| GDP per capita (current US$) | `NY.GDP.PCAP.CD` |
| GDP growth (annual %) | `NY.GDP.MKTP.KD.ZG` |
| Population, total | `SP.POP.TOTL` |
| Poverty headcount ratio at $2.15/day (%) | `SI.POV.DDAY` |

### Source-scoped data API

**Path:** `/v2/sources/{sourceId}/country/{codes}/series/{seriesId}[/time/{tokens}][/{concept}/{value}]?format=json`. Segments may appear in any order, and an omitted concept matches every value of it — `country` and `time` included. Ids are case-insensitive.

**Discovery:** `/v2/sources/{id}/concepts` lists the source's concepts (3 or 4 in all 71 sources); the lowercased concept id lists its values at `/v2/sources/{id}/{concept}` (`version`, `classification`, `sector`, `counterpart-area`, `country`, `time`) as `source[0].concept[0].variable[] = {id, value}`. Measured extra dimensions: `Version` (57, 139 releases, ascending, labels like `2025 Mar`), `Classification` (single value on PEFA 67/68/79/91/85 and Food Prices for Nutrition 88; 16–17 measures on ICP 62/71/78/90; 8 methodology releases on FPN Datahub Archive 93), `Sector` (GDLD 80, 65 sectors), `Counterpart-Area` (IDS 6 and DSSI 81, 304 values including `WLD` World). The concepts listing also carries the source name, with a leading space on DSSI.

**Lists:** `;`, URL-encoded as `%3B`. A comma fails. An unknown member of a list is dropped silently (`SDN;ZZZ` returns Sudan alone), which is why every segment is validated first.

**Countries:** the source's own three-character codes only — `SDN` works, `SD` is rejected. Listings include legacy codes (`ADO`, `YUG`, `ZAR`) and omit some aggregates `/country` has.

**Time:** tokens, not years, and the grammar varies: `YR2015` (label `2015`), `YR201806` (PEFA assessment month, label `Jun.18`), `YR2027-M11` (DSSI monthly projection, label `2027 M11`). There is no range: `time/YR2010:YR2015` answers HTTP 302 to an error page. `mrv` follows the standard endpoint's rule within the scope, but an unpinned dimension is part of that scope: `SDN` for `SM.POP.REFG.OR` with `mrv=1` and no version returns `YR2023` for all 139 releases, whether or not a release holds a value there.

**Envelope:** a single object — `{page, pages, per_page, total, lastupdated, source: {id, name, data: [{variable: [{concept, id, value}], value}]}}` — with one `variable` entry per concept in no stable order. `value` is a number or `null`. Row order changes with the shape of the request (`country/all` sorts by country then ascending year; an explicit list keeps its order). `per_page=20000` returned 19,564 rows in one page.

**Cube shape:** every source sampled (57, 67, 68, 78, 79, 80, 81, 88, 91) returned a row for every country × period × dimension value in scope, nulls included — `SM.POP.REFG.OR` for 8 countries × 5 years is 5,560 rows, 139 releases each.

**Errors:** an unknown source, series, country, or dimension value is HTTP 200 with `content-type: text/xml` and `<wb:error><wb:message id="160" key="Data not found.">The provided parameter value is not valid or data not found.</wb:message></wb:error>`, whatever `format` says. The service reads that envelope as an empty result, which after segment validation is the only thing it can mean.

### Poverty and Inequality Platform

**Base URL:** `https://api.worldbank.org/pip/v1/` — not `pip.worldbank.org/api/v1`, which is the web front-end and serves an HTML app shell.

**Endpoints used:** `/pip?country=&year=&povline=&welfare_type=&reporting_level=&version=&fill_gaps=` for economies, `/pip-grp?country=&year=&povline=&version=&group_by=` for aggregates, `/versions` to resolve `version`, and `/aux?table=regions` and `/aux?table=country_list` as reference tables. `country` takes one ISO3 code, a comma-separated batch, or `all`; `year` takes a year, `all`, or `MRV`. Codes are case-insensitive and unknown query parameters are ignored.

**`/pip` accepts surveyed economies only by code.** Its `country` list holds the 172 surveyed economies, the 27 codes of `/aux?table=regions`, and `ALL`; the 46 economies PIP publishes only as `CMD estimation` rows (`AFG`, `BHR`, `GUM`) answer HTTP 404 by code but appear under `country=all&fill_gaps=true`. `/aux?table=country_list` lists all 218 economies (including `TWN`, which the World Bank country listing lacks), and `/aux?table=countries` the 172 surveyed ones.

**`/pip-grp`:** the same row-array envelope, one row per aggregate × year, with `region_code`, `region_name`, `reporting_year`, `poverty_line`, `reporting_pop`, `headcount`, `poverty_gap`, `poverty_severity`, `watts`, `mean`, `pop_in_poverty`, `spr`, `pg`, and `estimate_type` (`actual`, `nowcast`, `projection`; release 20260922 runs 1981–2026, `nowcast` from 2025). `group_by` selects the grouping — `wb` serves the seven regions, `AFE`/`AFW`, and `WLD`; `incgroup` the four income groups; `ida` `IDA`/`IBRD`/`BLND`/`REST`; `fcv` and `regionpcn` their own codes — and a code of another grouping answers `[]`. `group_by=world` answers HTTP 500. An economy code is HTTP 400. `year=MRV` answers `[]`, and an omitted `year` returns the full series. `fill_gaps` is ignored; `welfare_type=income` narrows an aggregate to its income-surveyed sliver (`SSF` 2022: 119,878 people) and `reporting_level=urban` answers HTTP 500. `version` is honored, and a rejected `year` is the same 404 as `/pip`'s.

**Response envelope:** a flat JSON array of row objects. No pagination and no paging metadata — the whole result set arrives at once (`country=all&year=all` is ~2,600 survey rows, ~10,100 gap-filled).

**Error convention:** real HTTP status codes. A rejected parameter value is HTTP 404 with `{"error": [...], "details": {"<param>": {"msg": [...], "valid": [...]}}}`, one `details` entry per rejected parameter, `country` always first. One bad code fails the whole batch (`country=USA,ZZZ` → 404). A well-formed query matching nothing is HTTP 200 with `[]`. An aggregate country code on `/pip` is HTTP 500 with a body carrying no detail beyond `Internal Server Error`.

**Input leniency:** country codes and `year` are case-insensitive (`usa`, `mrv`), unknown query parameters are ignored, and `povline` accepts 0–2700. An empty or absent `country` is read as every economy, so a caller must never let an empty value reach the query string.

**Row grain:** country × reporting year × reporting level × welfare type. Ten economies publish more than one `reporting_level` (only China all three) and thirty-five publish both an income and a consumption series, so the country code alone does not identify a row. `survey_year` may be fractional when the survey spans a fiscal year (India's 2022 HCES reports `2022.58`).

**`estimation_type`:** `survey`, `interpolation`, `extrapolation`, or `CMD estimation` — the last for economies PIP holds no survey for. `is_interpolated` is `true` on the interpolated and extrapolated rows only, so it does not by itself separate survey rows from gap-filled ones.

**Mode asymmetry:** `fill_gaps=true` is a different series, not a superset. It spans 1981–2026 for every economy, drops the whole distributional block from every row it returns, and reports a slightly different `headcount` for a year both modes cover (`USA&year=2022`: `0.014` survey, `0.0132` gap-filled). `fill_gaps=false` spans only the survey years, which for some economies (`USA`) start well before 1981.

**Versions:** `/versions` lists every data release × PPP vintage as `{version, release_version, ppp_version, identity}`, newest release first — `20260324` at `2021` and `2017` as of 2026-09-12. `/pip` accepts either the fully-qualified `version` (`20260324_2017_01_02_PROD`) or `ppp_version` alone, which resolves to that vintage's newest release; with neither it serves the newest release at its newest vintage. The listing outlives what `/pip` serves: measured 2026-09-12, only the two newest releases answered, and every older one — each 2011-vintage build included — returned HTTP 500 on repeated requests. A `version`-pinned query is cached by PIP separately from the unpinned form of the same query, so each pays its own cold computation once.

**Not exposed:** the FCV (`group_by=fcv`) and PovcalNet (`group_by=regionpcn`) aggregates, and the `/aux` tables beyond the two read for routing.

### Projects

**Base URL:** `https://search.worldbank.org/api/v3/` — a different host from the other two, not `api.worldbank.org/v2/projects`.

**Endpoint used:** `/projects?format=json&fl=&rows=&os=&srt=boardapprovaldate&order=desc&qterm=&<field>_exact=&strdate=&enddate=`. No key.

**Response envelope:** `{rows, os, page, total, projects: {<project_id>: {...}}, facets}`. `projects` is an object keyed by project ID, not an array, so the values have to be collected before anything can treat them as rows. `total`, `os`, and `page` are strings; `rows` is a number.

**Pagination:** offset-based on `os` (skip) and `rows` (page size), not `page`/`per_page`. Default `rows` is 10. `rows` is capped at 1,000 — a larger value is accepted and echoed back in the envelope while 1,000 records are returned. `os` accepts 0–100,000; outside that the request fails with HTTP 400.

**Error convention:** three shapes, none of them the sentinel envelope Indicators v2 uses. A bad parameter *value* on an `_exact` filter is HTTP 200 with `total: 0` and no error at all. A bad parameter *type* is HTTP 400 with a JSON body naming the Azure Search cluster and index behind the API. A value the query builder cannot parse — a `strdate` whose month is outside 01–12 (`2020-13-01`, `2020-00-15`) — is HTTP 500 with a `text/txt` body holding a Node stack trace and absolute paths from the upstream host; an out-of-range day (`2020-02-30`, `2023-02-29`) is accepted with HTTP 200 and searched as though it existed, and a reversed `strdate`/`enddate` window answers HTTP 200 with `total: 0`. An unrecognized path is HTTP 404 with a Tomcat HTML error page. None of these bodies are quoted into a message.

**Unknown parameters are ignored,** so a misspelled filter name silently widens the search to the full portfolio rather than erroring.

**Field projection:** `fl` is a comma-separated field list and is required to reach `status`, `countrycode`, `countryname`, and `project_abstract`, none of which are in the default projection. It does not narrow the response to exactly what was asked for: `proj_id` and `project_abstract` come back regardless. `fl=*` returns the full field inventory (45 fields), including the `_exact` variants.

**Filters confirmed to narrow a result:** `qterm` (free text over name, abstract, and objective; terms combine as AND), `countrycode_exact` (ISO2 — `BRA` matches nothing, `BR` matches 831), `status_exact`, `regionname_exact`, `countryshortname_exact`, `sector_exact`, `sectorcode_exact`, `theme_exact`, `mjsector_exact`, `prodline_exact`, `projectfinancialtype_exact`, `esrc_ovrl_risk_rate_exact`, `cons_serv_reqd_ind_exact`, plus `strdate`/`enddate` (an inclusive board-approval window) and `fiscalyear`. **Accepted and ignored:** `borrower_exact`, `impagency_exact`, `teamleadname_exact`, `lendinginstr_exact`, `fiscalyear_exact`, `majorsector_exact`.

**Multi-value syntax:** `^`. A comma is read as part of a single value and matches nothing; a repeated parameter keeps only the first occurrence. Values within one filter combine as OR, and separate filters combine as AND.

**Facets:** `fct=<field>_exact` returns value counts as an object keyed by ordinal, capped at 100 entries. They are scoped to the current query, so a zero-hit search returns an empty `facets` object and they cannot serve as a recovery path from one. `countrycode_exact`, `prodline_exact`, `mjsector_exact`, and `sectorcode_exact` are filterable but not facetable.

**Default ordering:** without `qterm`, board approval date, descending — nulls last. With `qterm`, descending project ID, not relevance and not board date (0 ID-order violations across 2,410 rows of three queries, measured 2026-09-25). `srt=boardapprovaldate&order=desc` restores board-date order under `qterm` and leaves the unfiltered order unchanged; `order` defaults to `desc`, and an unknown `srt` field is ignored. Pagination under it is contiguous and repeatable, ties included — two 50-row pages equal one 100-row page. The service sends it on every request.

**Measured 2026-08-09:** 28,074 projects total — 18,293 Closed, 6,901 Dropped, 2,581 Active, 299 Pipeline, across nine operational regions and 218 distinct country codes, 34 of which are World Bank regional codes carrying a digit. Board approval dates span 1947-05-09 to 2027-10-26. Abstracts are published for 52% of the portfolio, with a median length of ~1,200 characters (p90 ~2,300, max 8,000); a 50-row page is ~111 KB with them and ~53 KB without. No rate-limit headers observed.

**Not exposed:** facet retrieval, a caller-selectable sort, and the sector/theme/product-line/risk-rating filters, whose value vocabularies are large, partly facet-invisible, and split across `FY17 - ` and unprefixed vintages.
